# Seicure — 설계 문서

파일 암호화 도구. 네이티브 C++ (MSVC/MinGW), .NET 비의존, 외부 런타임 DLL 없이 단일 실행 파일 배포.

**핵심 목표:** 파일 내용뿐 아니라 **파일명, 타임스탬프, 속성, 크기 정보까지 은닉**하고, 복호화 시 원본을 그대로 복원한다.

---

## 1. 위협 모델

**방어 대상**

- 분실/도난된 디스크, USB에 담긴 파일의 내용 노출
- 클라우드 스토리지 사업자 및 침해 사고
- 제3자 전달 시 전송 구간 노출
- 암호문 변조 — 1비트라도 바뀌면 복호화가 실패해야 한다
- **메타데이터 노출** — 파일명(`2026_구조조정안.hwp` 같은), 작성/수정 시각, 파일 크기

**방어하지 못하는 것 (문서·UI에 명시)**

- 사용 중인 PC에 이미 설치된 악성코드, 키로거
- 약한 비밀번호 — KDF로 시간을 벌 뿐이다
- 비밀번호를 아는 사람
- **파일 크기의 근사치** — 3.3절 참조. 완전 은닉은 불가능하다.

## 2. 암호 설계

### 2.1 원칙

암호 프리미티브를 직접 구현하지 않는다. 검증된 구현만 사용한다.

### 2.2 선택

| 항목 | 선택 | 근거 |
|---|---|---|
| 대칭 암호 (기본) | **XChaCha20-Poly1305** | 상수 시간, 하드웨어 의존 없음, 192비트 논스 |
| 대칭 암호 (선택) | AES-256-GCM | NIST 승인 알고리즘이 요구되는 배포용 |
| KDF | Argon2id (`m=256MiB, t=3, p=1`) | 메모리 하드. GPU/ASIC 병렬 공격에 강함 |
| 구현 | **libsodium 1.0.22** (벤더링, 정적 링크) | 감사받은 단일 구현, 3개 플랫폼 공통 |
| 난수 | `randombytes_buf` | libsodium이 OS CSPRNG를 감쌈 |

**왜 XChaCha20이 기본인가.** 소프트웨어 AES는 테이블 참조를 쓰므로 캐시 타이밍으로 키가 샌다. 하드웨어 가속이 있어야 안전한데, 그 가속은 CPU마다 유무가 다르다. ChaCha20은 덧셈·회전·XOR만 쓰므로 **어느 CPU에서든 구조적으로 상수 시간**이다. 논스도 192비트라 카운터 관리에 여유가 크다.

**AES를 남겨둔 이유.** 공공·금융 조달에서 FIPS 승인 알고리즘을 명시적으로 요구하는 경우가 있다. `cipher_id`로 두 알고리즘을 모두 지원하므로, 그런 요구가 생기면 **기본값만 바꾸면 되고 포맷 변경이 없다.** 복호화는 항상 헤더를 따르므로 두 종류가 섞여 있어도 문제없다.

AES-256-GCM은 하드웨어 지원이 없는 CPU에서 사용 자체를 거부한다(`cipher_available()`). 소프트웨어 폴백을 두면 부채널이 열리므로, 느리게 동작시키는 것보다 거부하는 편이 옳다.

**병렬도가 1인 이유.** libsodium의 `crypto_pwhash`는 레인 수를 노출하지 않는다. 멀티코어에서 벽시계 시간은 손해지만, 공격자는 어차피 추측 단위로 병렬화하므로 방어력 손실은 없다.

**직접 구현하지 않는 원칙은 그대로다.** 오히려 강화됐다 — 이전에는 Argon2(벤더링)와 CNG(OS) 두 곳에 의존했으나 지금은 감사받은 libsodium 하나로 통일됐다.

### 2.3 키 계층

```
비밀번호 ──Argon2id(salt, params)──> KEK (32B)
                                      └─ AES-256-GCM으로 DEK 언랩
DEK (32B, 파일마다 랜덤) ──────────> 메타데이터 + 본문 암호화
```

## 3. 파일 포맷 v1

### 3.1 전체 구조

```
┌─────────────────────────────────────────┐
│ 평문 헤더 (72B)                          │  ← 최소한의 정보만
├─────────────────────────────────────────┤
│ 암호화된 메타데이터 블록 (고정 1024B+16B) │  ← 파일명, 시각, 속성, 실제 크기
├─────────────────────────────────────────┤
│ 암호화된 본문 청크 (패딩 포함)            │
└─────────────────────────────────────────┘
```

### 3.2 평문 헤더

복호화에 반드시 필요한 값만 남긴다. **파일 크기 정보는 여기 두지 않는다.**

```
오프셋  크기  필드
0       6     magic         "SEICUR"
6       1     format_ver    1
7       1     cipher_id     1 = AES-256-GCM
8       1     kdf_id        1 = Argon2id
9       3     reserved      (0으로 채움)
12      4     kdf_mem_kib       (LE)
16      4     kdf_iterations    (LE)
20      4     kdf_parallelism   (LE)
24      16    kdf_salt          (랜덤)
40      4     chunk_size        (기본 1 MiB)
44      8     base_nonce        (랜덤)
52      12    dek_wrap_nonce
64      32    wrapped_dek
96      16    dek_wrap_tag
─────────────────────────────────────────
112           메타데이터 블록 시작
```

**헤더 무결성.** 별도 MAC을 두지 않는다. DEK 언랩(AES-256-GCM)의 **AAD로 0~51 바이트 전체**를 넣으면 어떤 필드든 변조 시 GCM 태그 검증이 실패한다. KDF 파라미터를 몰래 낮추는 다운그레이드 공격도 이걸로 막힌다.

### 3.3 메타데이터 블록 — 파일명·속성 은닉

평문 1024바이트 **고정 크기**로 직렬화한 뒤 암호화한다. 고정 크기여야 파일명 길이조차 새어나가지 않는다.

```
오프셋  크기  필드
0       8     original_size      실제 원본 크기 (패딩 제거용)
8       8     creation_time      FILETIME
16      8     last_write_time    FILETIME
24      8     last_access_time   FILETIME
32      4     file_attributes    읽기전용/숨김/시스템/보관
36      4     entry_count        아카이브 항목 수
40      2     name_len           파일명 길이 (UTF-16 코드 유닛 수)
42      1     content_type       0=단일 파일, 1=아카이브
43      1     meta_flags         bit0=윈도우 속성 유효, bit1=POSIX 모드 유효
44      4     posix_mode         POSIX 권한 비트 (& 07777)
48      510   original_name      UTF-16LE, 남는 공간은 0으로 채움
558     466   padding            0으로 채움
─────────────────────────────────────
1024          → AEAD 암호화 → 1024B + 태그 16B
```

**권한을 두 벌로 저장하는 이유.** 윈도우의 `FILE_ATTRIBUTE_*`와 POSIX의 모드 비트는 서로 대응되지 않는다. 숨김 속성에 해당하는 POSIX 개념이 없고, 실행 비트에 해당하는 윈도우 개념이 없다.

그래서 **각 플랫폼이 아는 것을 기록하고 `meta_flags`로 무엇을 채웠는지 밝힌다.** 0이 "설정 안 함"인지 "진짜 0"인지 읽는 쪽이 추측하지 않아도 된다.

대응되는 유일한 항목이 읽기 전용이다. 윈도우에서 만든 컨테이너를 맥에서 열면 `0444`/`0644`로, 반대 방향이면 `FILE_ATTRIBUTE_READONLY`로 옮긴다. **실행 비트는 절대 만들어내지 않는다** — 근거 없는 보안 결정이 되기 때문이다.

`st_mode`의 파일 종류 비트는 파싱 시 잘라낸다. 원본 객체를 설명하는 값이지 새로 만들 파일의 것이 아니다.

**시각은 어디서나 FILETIME 틱(1601년 기준 100ns)으로 저장한다.** 어떤 파일 시스템보다 정밀하므로 POSIX 쪽은 변환만 하면 손실이 없다. 0은 "모름"이다 — 리눅스는 `stat()`으로 생성 시각을 주지 않는다.

NTFS 파일명 최대 255자(UTF-16 기준 510바이트)이므로 510바이트면 충분하다.

**복원 순서 주의.** `last_access_time`은 파일을 쓰는 행위 자체로 갱신되므로, 내용을 모두 쓰고 핸들을 닫기 직전에 `SetFileTime`으로 세 시각을 한 번에 복원해야 한다.

### 3.4 크기 은닉 — Padmé 패딩

**먼저 한계를 분명히 한다. 파일 크기의 완전한 은닉은 불가능하다.** 10GB 파일을 1KB처럼 보이게 만들 수는 없다. 현실적인 목표는 *유출되는 정보량을 최소화*하는 것이다.

두 가지를 적용한다.

1. 평문 헤더에서 크기 필드를 제거하고, 실제 크기는 암호화된 메타데이터 블록에만 둔다 (3.3)
2. 본문을 **Padmé** 스킴으로 패딩해 파일 길이를 성긴 구간(bucket)으로 뭉갠다

Padmé는 PURB 논문(Nikitin et al., 2019)에서 제안된 방식으로, 누출을 상위 몇 비트로 제한하면서 오버헤드를 **최대 약 12%** 이내로 억제한다.

```
padme(L):
    if L < 16: return 16
    E    = floor(log2(L))          # 지수
    S    = floor(log2(E)) + 1      # 유효 비트 수
    z    = E - S
    mask = (1 << z) - 1
    return (L + mask) & ~mask      # 2^z의 배수로 올림
```

실제 오버헤드는 100B → 104B (4%), 1MB → 약 1.58%. 파일이 클수록 비율이 낮아진다.

패딩은 0으로 채우며, AEAD 내부에 있으므로 암호문상으로는 구분되지 않는다. 복호화 시 메타데이터의 `original_size`로 잘라낸다 — 이 값은 인증된 값이므로 신뢰할 수 있다.

**더 강한 은닉이 필요하면** 고정 크기 컨테이너(VeraCrypt 볼륨 방식)만이 답이다. 향후 확장 항목으로 남긴다.

### 3.5 본문 청크

대용량 파일을 통째로 메모리에 올릴 수 없으므로 청크 단위로 처리한다. **자체 구현 도구들이 가장 많이 틀리는 지점이다.**

```
청크 i: [ 암호문 (chunk_size) ][ GCM 태그 16B ]
```

- **논스**: `base_nonce(8B) || counter(4B, BE)` = 12B. DEK가 파일마다 랜덤이고 counter가 단조 증가하므로 논스 재사용이 구조적으로 불가능하다.
- **AAD**: `block_type(1B) || block_index(8B, BE) || is_final(1B)`

| 블록 | counter | block_type | block_index |
|---|---|---|---|
| 메타데이터 | 0 | 0 | 0 |
| 본문 청크 i | i+1 | 1 | i |

AAD 각 필드의 역할이 다르다.

- `block_index` → 청크 **순서 바꿔치기** 탐지
- `is_final` → 파일 뒷부분을 잘라내는 **절단 공격** 탐지. 이 플래그가 없으면 잘린 파일이 정상으로 보인다.
- `block_type` → 메타데이터 블록과 본문 청크의 **혼동 공격** 차단

STREAM 구성(Hoang et al., 2015)과 동일한 검증된 패턴이다.

**한계.** GCM은 동일 키로 2^32회 미만 호출을 권장. 1MiB 청크 기준 이론상 4PiB까지 가능하므로 실사용 문제없다.

### 3.6 출력 파일명

**파일명을 안에서 암호화해도 출력 파일을 `보고서.hwp.sef`로 저장하면 의미가 없다.** 기본값은 원본과 무관한 랜덤 이름으로 한다.

```
<32자리 랜덤 hex>.sef
```

사용자가 직접 지정하는 것도 허용한다. 대신 파일 식별이 어려워지는 것은 메타데이터 은닉의 본질적 대가이며, UI에서 이를 설명해야 한다.

## 4. 구현상 주의점

### 4.1 메모리 위생

- 키/비밀번호 버퍼는 `SecureZeroMemory`로 소거 (컴파일러 최적화로 제거되지 않음)
- `VirtualLock`으로 페이지 파일 기록 방지
- 비밀번호에 `std::string` 금지 — 재할당 시 평문 사본이 힙에 남는다
- RAII 래퍼(`SecureBuffer`)로 강제

### 4.2 안전한 파일 쓰기

원본 파괴는 되돌릴 수 없으므로 순서가 중요하다.

1. 임시 파일에 출력
2. `FlushFileBuffers`로 디스크 동기화
3. **복호화 검증 통과 확인**
4. `ReplaceFileW` / `MoveFileExW`로 원자적 교체
5. 그 다음에야 원본 처리

실패 시 임시 파일을 정리하고 원본은 손대지 않는다.

**다중 파일 추출은 전부-아니면-전무여야 한다.** 개발 중 실제로 발견한 결함인데, 항목별로 완료되는 즉시 커밋하면 컨테이너 뒷부분이 변조됐을 때 앞쪽 파일들이 디스크에 남는다. 공격자가 뒤를 잘라내 원하는 일부만 추출되게 유도할 수 있고, 사용자는 오류를 놓치고 추출이 됐다고 착각한다.

그래서 `AtomicFileWriter`를 `finalize()`(플러시·시각 복원·핸들 닫기)와 `publish()`(원자적 이동)로 분리했다. 항목들은 임시 파일 상태로 대기하다가 **컨테이너 전체가 인증된 뒤에만** 일괄 반영된다. 중간에 실패하면 소멸자가 임시 파일을 모두 지운다. 열린 핸들은 항상 1개로 유지된다.

**원본 안전 삭제.** 제공하되 SSD의 wear leveling과 TRIM 때문에 **덮어쓰기가 물리적 삭제를 보장하지 않는다**는 점을 UI에 명시한다. 숨기면 사용자를 오도하는 것이다.

### 4.3 기타

- CLI 비밀번호 입력은 `SetConsoleMode`에서 `ENABLE_ECHO_INPUT` 해제
- **파이프로 들어온 비밀번호는 UTF-8 BOM을 제거한다.** PowerShell은 네이티브 프로세스로 문자열을 파이프할 때 `EF BB BF`를 앞에 붙인다. 제거하지 않으면 스크립트로 암호화한 파일을 나중에 프롬프트에 직접 입력해 열 수 없다 — 조용한 데이터 손실이다
- 진행률/취소를 위해 작업은 워커 스레드에서 (GUI 스레드 블로킹 금지)
- 경로는 전 구간 UTF-16 (`W` API), 긴 경로(`\\?\`) 지원

## 5. 프로젝트 구조

```
Seicure/
├─ CMakeLists.txt
├─ docs/DESIGN.md
├─ src/
│  ├─ core/            # 플랫폼·UI 비의존. 테스트 가능한 순수 로직
│  │  ├─ secure_buffer.hpp
│  │  ├─ crypto.hpp/cpp        # CNG 래퍼 (AES-GCM, RNG)
│  │  ├─ kdf.hpp/cpp           # Argon2id
│  │  ├─ format.hpp/cpp        # 헤더/메타데이터 직렬화, Padmé
│  │  └─ stream.hpp/cpp        # 청크 암복호화 엔진
│  ├─ platform/        # Win32 파일 I/O, 메타데이터 보존, 보안 메모리
│  ├─ cli/
│  └─ gui/
├─ third_party/argon2/
└─ tests/
```

`core`가 Win32 GUI에 의존하지 않는 것이 핵심이다. 테스트가 가능해지고 CLI와 GUI가 같은 엔진을 공유한다.

**플랫폼 계층만 OS를 안다.** `platform/`이 OS를 호출하는 유일한 곳이고, 빌드 시 `file_win32.cpp`/`console_win32.cpp` 또는 `file_posix.cpp`/`console_posix.cpp`가 선택된다. 이식은 여기에 파일을 추가하는 일이지 위쪽을 건드리는 일이 아니다.

경로는 계층 경계를 `std::wstring`으로 넘나든다. 위쪽 코드가 전부 그렇게 쓰여 있기 때문이고, POSIX 구현이 시스템 콜 직전에 UTF-8 바이트 문자열로 변환한다.

**검증 상태.** Ubuntu 24.04 (GCC 13.3)에서 실제로 빌드하고 테스트 65개를 통과시켰다. 양방향 상호운용성도 확인했다 — 윈도우에서 만든 컨테이너를 리눅스에서, 리눅스에서 만든 컨테이너를 윈도우에서 열어 내용·한글 파일명·시각·권한이 모두 보존되는 것을 확인했다. 읽기 전용 매핑도 양방향으로 동작한다(리눅스 `0444` ↔ 윈도우 `READONLY`).

**하드닝은 플랫폼별로 다르다.** PE와 ELF는 링커 옵션이 다르므로 `WIN32` 여부로 나눈다. 윈도우는 `--dynamicbase --nxcompat --high-entropy-va`와 정적 링크, POSIX는 `-z relro -z now -z noexecstack`과 PIE다. **리눅스에서는 정적 링크를 기본으로 두지 않는다** — glibc를 정적 링크하면 NSS가 깨지고, 리눅스 사용자가 기대하는 방식도 아니다.

**알려진 한계.** POSIX 파일명은 유효한 UTF-8이 아닐 수 있는데, 현재 구조는 UTF-8을 가정한다. 드문 경우지만 그런 이름은 왕복에서 깨진다.

## 6. 개발 순서

**CLI를 먼저 만든다.** GUI 없이 전체 기능을 검증할 수 있고, GUI는 결국 core 위의 껍데기다.

| 단계 | 내용 | 완료 기준 | 상태 |
|---|---|---|---|
| M0 | CMake 스켈레톤, 테스트 하네스, Argon2 벤더링 | 빈 테스트 통과 | **완료** |
| M1 | crypto + kdf | GCM 규격 KAT, Argon2id 공식 벡터 통과 | **완료** |
| M2 | format + Padmé + stream 엔진 | 왕복/변조/절단 테스트 통과 | **완료** |
| M2.5 | archive 계층 (다중 파일) | 경로 탈출 차단, 항목 수 은닉 | **완료** |
| M3 | platform 메타데이터 보존 + CLI | 파일명·시각·속성 완전 복원 | **완료** |
| M4 | Win32 GUI | 드래그앤드롭, 진행률, 취소 | **완료** |
| M5 | 하드닝, 패키징 | 단일 exe, 서명 | 진행 예정 |

현재 61개 테스트 통과 (`build\tests\seicure_tests.exe`).

CLI와 GUI 모두 실파일로 동작한다. 40MB 파일 왕복 0.4초, 한글 파일명·타임스탬프·속성 완전 복원, GUI 암호화 → CLI 복호화 교차 검증 완료.

## 6.5 계층 구조

```
core  →  platform  →  job  →  { cli, gui }
```

`job` 계층이 "파일들을 암호화한다"를 담당한다. CLI와 GUI가 같은 코드를 쓰므로 두 프론트엔드가 어긋날 수 없다 — 실제로 GUI를 붙이면서 CLI에 있던 로직을 이 계층으로 끌어올렸다.

## 6.6 GUI 설계

90년대 인광(phosphor) 터미널의 시각 언어를 따른다. 녹색이 감도는 근흑색 바탕, 밝은 형광 녹색 액센트 하나, 전면 모노스페이스, 최소한의 크롬. 구조는 상자와 구분선이 아니라 여백과 서체 굵기로 표현한다.

**팔레트 원칙.** 바탕은 순수 검정(`#000000`)이고, 그 위의 회색 계열은 전부 녹색을 머금는다. 전체가 다크 모드 앱이 아니라 CRT 화면처럼 읽히게 하기 위함이다. 신호는 형광 녹색 하나가 담당한다.

**시대 표현.** 색만으로는 부족해서 형태와 동작까지 맞췄다.

- 모서리 반경 2px. 6px는 모던 앱 카드로 읽히고, 각진 모서리라야 터미널로 읽힌다
- 빈 바탕에만 3px 간격 **스캔라인**을 깐다. 텍스트 위에 겹치면 진짜 CRT에 가깝지만 본문 대비를 3분의 1 깎아먹는다. 효과보다 가독성이 우선이다
- 진행률은 매끈한 막대가 아니라 **문자 게이지** `[████░░░░] 47%`
- 로그 마커는 `[OK]` / `[!!]` / `[--]`
- 상태줄 끝에 530ms 주기로 **깜빡이는 블록 커서**. 커서만 다시 그리면 되므로 상태줄 영역만 무효화하고 `WM_PAINT`도 손상 영역만 blit한다 — 초당 두 번 전체 창을 다시 그릴 이유가 없다
- 버튼·모드·제목은 대문자

유일한 예외가 **오류 색이다.** 경고는 명확해야 하는데 "조금 다른 녹색"으로는 구분되지 않는다. 그래서 오류만 의도적으로 녹색 계열을 벗어난 붉은색을 쓴다.

색은 `src/gui/theme.hpp` 한 곳에 모여 있고, `tools/make_icon.ps1`의 `$BG`/`$MARK`가 그중 `BG`와 `ACCENT`를 따라간다. 팔레트를 바꾸면 두 곳을 같이 고쳐야 한다.

- 표준 Win32 컨트롤은 쓰지 않고 GDI로 직접 그린다 (더블 버퍼링)
- 예외는 **비밀번호 입력의 EDIT 컨트롤** 하나다. 한글 IME, 클립보드, 캐럿, 선택을 직접 구현하는 것은 위험하다
- 콘텐츠 폭에 상한(620)을 두고 중앙 정렬한다. 초광폭 모니터에서 최대화하면 비밀번호 입력란이 3800px로 늘어나 망가진다

### 커스텀 프레임

OS 기본 타이틀바를 쓰지 않고 앱 헤더 자체가 제목 표시줄이다.

- `WM_NCCALCSIZE`에서 **위쪽 프레임만** 클라이언트 영역으로 회수한다. 좌·우·아래 프레임은 `DefWindowProc`에 맡기는데, 이것이 리사이즈·스냅·그림자를 네이티브로 유지하는 핵심이다
- 최대화 시에는 창이 모니터 밖으로 프레임 두께만큼 넘어가므로 위쪽을 `SM_CYFRAME + SM_CXPADDEDBORDER`만큼 들여쓴다. 안 하면 캡션이 화면 밖으로 나간다
- `WM_NCHITTEST`에서 네 변·네 모서리는 `HT*` 리사이즈 코드를, 캡션 영역은 `HTCAPTION`을 반환한다. `HTCAPTION` 하나로 드래그, 더블클릭 최대화, 스냅 레이아웃, 시스템 메뉴가 전부 따라온다
- 최소화·최대화·닫기 버튼은 직접 그리고 해당 영역만 `HTCLIENT`로 돌려 우리가 클릭을 받는다
- 글리프는 심볼 폰트가 아니라 GDI 선으로 그린다. Segoe MDL2가 있으리라는 보장이 없고 어차피 직선 몇 개다
- `CreateWindow`는 물리 픽셀을 받으므로 창 생성 후 DPI를 읽어 크기를 다시 맞춘다. 안 하면 150% 환경에서 창이 1/3 작게 뜬다
- 작업은 워커 스레드에서 돌고 진행률은 `PostMessage`로 UI에 전달한다. 퍼센트가 바뀔 때만 보내 메시지 큐 범람을 막는다
- 작업 중 창을 닫으면 즉시 종료하지 않고 취소 신호를 보낸 뒤 워커가 정리를 마치면 닫는다. 중간에 죽이면 임시 파일이 남는다

### 아이콘

**모서리가 접힌 페이지에 열쇠구멍을 파낸 형태.** 접힌 모서리가 "파일", 열쇠구멍이 "잠김"을 뜻한다. 문서와 자물쇠를 나란히 놓지 않고 하나의 실루엣으로 통합했기 때문에 작은 크기에서도 무너지지 않는다.

`tools\make_icon.ps1`이 `assets\seicure.ico`를 생성한다. 손으로 그린 비트맵이 아니라 코드에서 나오므로 언제든 조정·재생성할 수 있다.

- 16/20/24/32/48/64/72/96/128/256의 10개 크기를 담는다. 256만 PNG 압축이고 나머지는 DIB다 — 작은 크기를 PNG로 넣으면 일부 셸 표면에서 문제가 생긴다
- **72와 96이 있는 이유**는 배율 150%에서 탐색기가 정확히 그 크기를 요청하기 때문이다(논리 48·64 × 1.5). 없으면 셸이 다른 크기를 늘리거나 줄여 마크가 흐려진다
- **128px 미만은 페이지를 그리지 않고 열쇠구멍만 그린다** (`-KeyholeBelow` 인자로 조정). 작은 크기에서 페이지 윤곽은 2~3픽셀짜리 테두리라 정보가 아니라 노이즈이고, 같은 공간을 두고 열쇠구멍과 경쟁해 둘 다 약해진다. 결과적으로 문서 형태는 "큰 아이콘"과 "아주 큰 아이콘" 보기에서만 나온다
- 크기에 따라 형태만 단순해지고 **색 역할은 고정이다.** 형광 녹색이 주체, 근흑색이 바탕. 작은 크기를 녹색 타일로 채우면 크기별로 색이 반전돼 다른 아이콘처럼 보인다
- 접힌 모서리가 3px 미만이 되면 없앤다 (현재는 40px 미만이 열쇠구멍 전용이라 자동으로 해당 없음)

**빌드 의존성 주의.** `.rc`의 `ICON` 참조는 CMake의 리소스 의존성 스캐너가 따라가지 않는다. `OBJECT_DEPENDS`로 명시하지 않으면 아이콘을 다시 만들어도 빌드가 "no work to do"로 넘어가고 예전 아이콘이 그대로 박혀 있다. 실제로 겪은 문제다.

창 캡션도 같은 아이콘 리소스를 `DrawIconEx`로 그린다. 작업표시줄과 창 안의 마크가 어긋날 수 없다.

**알려진 한계.** EDIT 컨트롤은 입력된 문자열을 자체 힙 버퍼에 보관하며 이를 우리가 지울 수 없다. 우리 쪽 사본은 `SecureBuffer`에 담아 소거하고 작업 완료 후 컨트롤을 비우지만, 컨트롤 내부 잔여물은 통제 범위 밖이다.

## 7. 테스트 계획

암호 도구는 **실패해야 할 때 실패하는지**가 더 중요하다.

- **KAT**: NIST AES-GCM 공식 벡터, RFC 9106 Argon2id 벡터
- **Padmé**: 경계값(0, 1, 15, 16, 2^n, 2^n±1) 및 오버헤드 12% 이내 검증
- **왕복**: 0바이트, 1바이트, `chunk_size` 정확히, `chunk_size ± 1`, 다중 청크, 대용량
- **메타데이터 복원**: 유니코드/한글/이모지 파일명, 각종 타임스탬프, 읽기전용·숨김 속성
- **변조 탐지 (필수)**
  - 암호문 1비트 반전 → 실패
  - GCM 태그 변조 → 실패
  - 헤더 KDF 파라미터 하향 조작 → 실패
  - 청크 순서 교환 → 실패
  - 파일 끝 절단 → 실패
  - 메타데이터 블록을 본문 청크 자리로 이동 → 실패
  - 잘못된 비밀번호 → 실패
- **은닉 검증**: 암호문 바이트열에 원본 파일명이 등장하지 않는지 확인
- **논스 유일성**: 동일 파일 반복 암호화 시 salt/nonce/DEK가 매번 달라지는지
- **크래시 안전성**: 중간 강제 종료 후 원본 무손상 확인

## 8. 빌드

현재 환경은 MinGW-w64 GCC 15.1.0 + CMake 4.0.2 + Ninja.

```
-std=c++20 -O2 -municode
-static -static-libgcc -static-libstdc++     # 단일 exe
-fstack-protector-strong
-Wl,--dynamicbase -Wl,--nxcompat -Wl,--high-entropy-va -Wl,--tsaware
-s -Wl,--no-insert-timestamp                 # 심볼 제거, 재현 가능 빌드
```

**MSVC 전환 여지.** CFG(`/guard:cf`)는 MSVC 전용이며 MinGW는 미지원. 배포 단계에서 MSVC + Windows SDK 전환을 권장한다. 코드 서명용 `signtool`도 Windows SDK에 포함된다. CMake 기반이므로 전환 비용은 낮다.

## 8.5 아카이브 계층 (다중 파일)

개별 처리와 다중 처리를 모두 지원한다.

- **개별 모드** (기본): 입력 N개 → 컨테이너 N개
- **아카이브 모드** (`--archive`): 입력 N개 → 컨테이너 1개. 파일 개수까지 은닉된다.

아카이브 페이로드는 단순 연결이다.

```
[Metadata 1024][데이터] [Metadata 1024][데이터] ...
```

항목 헤더가 컨테이너 메타데이터와 동일한 구조를 재사용하므로 직렬화 코드가 하나뿐이다. 항목 수는 인증된 컨테이너 메타데이터에만 있고, 페이로드 전체는 기존 Padmé 패딩 대상이라 **아카이브와 단일 파일 컨테이너는 외부에서 구분되지 않는다.**

**경로 탈출 차단이 필수다.** 아카이브는 내 손을 떠나는 순간 공격자 제어 입력이 된다. 항목 이름에 `..\..\Windows\System32\evil.dll` 같은 값이 들어오면 추출 디렉토리 밖에 파일을 쓸 수 있다. `is_safe_entry_name()`이 경로 구분자, 드라이브 콜론, 제어 문자, Win32가 조용히 잘라내는 후행 점·공백을 모두 거부한다.

## 8.7 설치 프로그램 (NSIS)

`installer/seicure.nsi`. Notepad++와 같은 도구를 쓴다 — 런타임 의존성 없는 네이티브 Win32 앱에 파일 연결과 우클릭 메뉴를 붙인다는 문제가 동일하다.

**시스템 전체 설치를 택했다.** `%LOCALAPPDATA%`에 설치하면 그 폴더는 해당 사용자로 실행되는 모든 프로세스가 쓸 수 있다. 악성코드가 권한 상승 없이 `seicure_gui.exe`를 바꿔치기할 수 있다는 뜻이고, 비밀번호를 받는 프로그램에서는 받아들이기 어렵다. `Program Files`는 ACL로 보호되며, 설치 시 UAC 한 번이 그 대가다.

등록 내용은 다음과 같다.

- `.sef` → `Seicure.Container` 형식, 아이콘, `shell\open`을 복호화 동사로 겸용 (더블클릭과 우클릭이 같은 곳으로)
- 모든 파일에 `*\shell\SeicureEncrypt` 암호화 동사

**동사는 `--encrypt` / `--decrypt`를 함께 넘긴다.** 그냥 파일 경로만 넘기면 사용자가 "복호화"를 눌렀는데도 똑같이 밝은 버튼 두 개 앞에 놓이게 된다. 플래그를 받으면 GUI가 비밀번호 칸에 포커스를 주고 상태줄로 안내하며, **Enter만 누르면 실행된다.** 우클릭 → 비밀번호 → Enter로 끝난다.

**단일 인스턴스가 필요하다.** 탐색기는 선택한 파일마다 프로세스를 하나씩 띄운다. 열 개를 고르면 창이 열 개 뜬다는 뜻이다. 이름 있는 뮤텍스로 먼저 뜬 창을 찾아 `WM_COPYDATA`로 경로를 넘기고 두 번째 프로세스는 즉시 종료한다. 실제로 4개를 동시에 실행해 창이 하나만 뜨는 것을 확인했다.
- 제어판 프로그램 목록 항목, 시작 메뉴 바로 가기
- 제거 시 전부 정리하되 **사용자의 `.sef` 파일은 건드리지 않는다**

**테스트 모드.** `/DTESTMODE`로 컴파일하면 권한 없이 HKCU에 쓰는 빌드가 나온다. 하이브만 다르고 파일 배치·레지스트리 구조·정리 로직은 동일하므로, 실제 시스템을 오염시키지 않고 전 과정을 검증할 수 있다.

**실제로 잡은 결함 두 가지.**

`MessageBox`는 무인 모드(`/S`)에서도 그대로 뜬다. 확인 대화상자를 그냥 두면 무인 제거가 영원히 멈추고, 더 나쁘게는 **업그레이드가 통째로 깨진다** — 설치 프로그램이 `.onInit`에서 이전 버전을 `/S`로 제거하며 `ExecWait`로 기다리기 때문이다. NSIS 정식 해법인 `/SD IDOK`로 두 대화상자 모두에 기본 응답을 지정했다. 테스트로 재현하지 않았다면 놓쳤을 문제다.

`Unicode true` 스크립트는 **BOM이 있는 UTF-8**이어야 한다. BOM이 없으면 한글 문자열에서 `Bad text encoding`으로 컴파일이 실패한다.
